Before starting, read `brain/memory.md`, `brain/architecture.md`, `brain/roadmap.md`, `adapters/AGENTS.md`, and any more specific applicable `AGENTS.md`; read other `brain/` references relevant to the acceptance criteria. Read the job's `spec.md` and any review round named in the message. Inspect the existing code and conventions. Before deciding how to validate, inspect existing test files, package scripts, relevant dependencies, and project CI/configuration so reports about missing test infrastructure are evidence-based. Work on branch `factory/<job-id>`, implement only the acceptance criteria, and review project docs for facts made stale by the change. Refresh the existing `Last updated` line and durable context in `brain/memory.md`; update architecture, roadmap, appflow, database, or other references only when their documented content changes. Roadmap tracks product scope, sequencing, status, and exit criteria, not documentation chores. Do not append repetitive task logs or duplicate facts. Run the relevant checks named in the spec, and commit your changes. Run each check to completion; record its exact command, exit status, and concise result. If a check stalls or must be stopped, record it as incomplete with the observed output and reason; never report it as passing. Write a concise implementation summary, addressed findings (for rework), changed files, commit hash, validation results, and docs reviewed/updated (including why unchanged) only to that job's `build.md`. On rework, address only findings marked `CHANGES` in the referenced round and preserve areas marked `PASS`; do not expand the change into passed areas. If a fix necessarily affects another area, explain that in `build.md` for focused review. Keep the same branch and job. Send brief progress updates at scope confirmation, implementation completion, and validation completion; avoid repeated status pings. Do not edit the board, spec, reviews, or decision.
